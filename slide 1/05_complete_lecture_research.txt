Linux kernel concurrency investigation, 2026-11-19.
Source lecture: https://www.cse.iitk.ac.in/users/swarnendu/courses/spring2026-cs636/concurrency-bugs.pdf

The governing mistake is treating a series of operations as safe because each individual operation appears safe. What must remain indivisible is the relationship between those operations. A lock on the wrong variable, an atomic counter, or a memory barrier on only one side may not enforce that relationship.

The files are cumulative: 01 is completely included in 02; 02 is completely included in 03; 03 is completely included in 04. Each .c file is a self-contained working Linux program with all previous functions built in. Neither compiling nor running a fixed kernel proves the historical defect still exists.

01_watch_queue.c exercises real notification-pipe, keyctl, and watch-queue kernel paths. It can activate an actual 2026 publication race when --watch-race is explicitly requested inside a disposable virtual machine. No userspace simulation is substituted for the bug. A no-crash result after N trials does not prove the kernel is safe. Hardware/platform and kernel configuration can block the path.

02_watch_queue_perf.c contains all of 01 plus real perf_event_open, mmap and PERF_EVENT_IOC_SET_OUTPUT. The safe test maps and redirects a kernel perf ring buffer but does NOT force map_range() to fail at the exact moment a second thread races. That additional fault injection / race scheduling is required for the historical 2026 perf UAF reproduction.

03_watch_queue_perf_ktls.c contains all of 02 plus an actual loopback TCP connection with Linux kTLS TX/RX, AES-GCM encryption and decryption. The cipher material is fixed for a local controlled integration test and must never be used in a deployed TLS connection. It does NOT force asynchronous crypto completion needed for the 2020 panic. Kernel CONFIG_TLS, TCP_ULP tls, and AES-GCM support are required.

04_full_linux_kernel_lab.c contains all of 03 plus a read-only kernel checker for trace, KCSAN, lockdep and perf restrictions. Missing pseudo-files do not establish a kernel configuration; check the actual .config of the target kernel. All four compile independently without modules or libraries beyond libc/pthreads.

Build each cumulative file independently:
    gcc -O2 -Wall -Wextra -Werror -pthread 04_full_linux_kernel_lab.c -o kernel_lab
    ./kernel_lab --audit --watch --perf --ktls

Only in a disposable VM whose crash and data loss you accept:
    ./kernel_lab --watch-race --vm-i-accept-crash

Before attempting a historical exploit/bug, inspect the exact running kernel source, verify the vulnerable functions exist, and check if the upstream fix has been backported. The program has no way to establish vulnerability from uname alone. Do not run the dangerous mode on your laptop's host kernel.

2026 kernel/watch_queue.c: actual syscall event chain, no hardware:
    pipe2(O_NOTIFICATION_PIPE) -> add_key -> KEYCTL_WATCH_KEY
    CPU A: watch_queue_set_size() allocates pages and bitmap
    CPU A: ordinary stores of notes, notes_bitmap, nr_pages, nr_notes
    CPU B: KEYCTL_SETPERM -> keyctl_setperm_key -> post_one_notification
    CPU B: sees nr_notes > 0 -> selects bitmap bit -> notes[0] is NULL -> crash
    WRONG: publishing four ordinary fields makes them observable as one unit.
    FIX: initialize pages and bitmap -> smp_store_release(&nr_notes, value)
         smp_load_acquire(&nr_notes) -> safely access pages and bitmap.
    Original 2026-10-08 patch proposed lock; 2026-10-09 v2 uses barriers.
    Upstream commit: 5e531d62f1f8834faf7a4eed0d41105cf6570a8f
    Primary: https://lkml.iu.edu/hypermail/linux/kernel/2610.1/04603.html
    Original: https://lists.openwall.net/linux-kernel/2026/10/08/2250
    Relevant lecture: ordering violations, data races, memory-model checking.

2022 kernel/watch_queue.c -> fs/pipe.c: separate bug in the same user API:
    producer under pipe->rd_wait.lock -> fills pipe_buffer -> plain pipe->head++
    consumer under pipe->mutex -> reads pipe->head -> accesses pipe_buffer
    WRONG: protecting producer and consumer with different locks guarantees visibility.
    FIX: smp_store_release(&pipe->head, head + 1), paired with
         smp_load_acquire(&pipe->head) in pipe_read().
    Upstream commit: 2ed147f015af2b48f41c6f0b6746aa9ea85c19f3
    Primary: https://lkml.rescloud.iu.edu/2203.1/07747.html
    Relevant lecture: happens-before and weak memory ordering.

2020 net/tls/tls_sw.c: completion is logically wrong despite atomic pending counter:
    CPU B: tls_decrypt_done atomic decrement makes decrypt_pending zero
    CPU B: evaluates async_notify true, about to call complete()
    CPU A: tls_sw_recvmsg reads pending zero, reinit_completion()
    CPU B: complete() fires for the already-finished request
    NEXT REQUEST: completion state is stale; wait can return too soon.
    WRONG: atomic decrement alone makes completion and reset atomic together.
    FIX: spin lock connects pending count and completion notification decisions.
    Upstream commit: 0cada33241d9de205522e3858b18e506ca5cce2c
    Primary: https://lists.openwall.net/netdev/2020/05/22/305
    Relevant lecture: atomicity violation without a simple data-race diagnosis.

2026 kernel/events/core.c: ring buffer lifetime is bigger than one mutex region:
    CPU A: perf_mmap holds mmap_mutex -> creates event->rb -> unlocks
    CPU A: map_range() later fails -> perf_mmap_close() cleans up ring buffer
    CPU B: PERF_EVENT_IOC_SET_OUTPUT -> ring_buffer_get() observes old event->rb
    CPU B: reference count increments after it may have hit zero -> warning/UAF
    WRONG: publishing event->rb under mutex protects its entire construction and cleanup.
    FIX: keep mmap_mutex held through map_range and its failure cleanup.
    Upstream commit: 77de62ad3de3967818c3dbe656b7336ebee461d2
    Primary: https://lkml.iu.edu/2603.0/09293.html (only original commit portion; later added LLM text is not primary evidence)
    Relevant lecture: atomicity / lifetime / shared-object interleavings.

2021 drivers/usb/gadget/composite.c: one CPU can deadlock itself:
    usb_function_deactivate holds cdev->lock -> usb_gadget_deactivate
    -> usb_gadget_disconnect -> composite_disconnect attempts cdev->lock AGAIN
    spin lock waits on lock already held by same CPU -> stalls / RCU stall reports
    WRONG: a function call that appears local cannot indirectly return to the lock.
    FIX: release spin lock around gadget deactivate/activate; restore afterward.
    Upstream commit: 5cc35c224a80aa5a5a539510ef049faf0d6ed181
    Primary: https://lkml.iu.edu/2101.1/02459.html
    Relevant lecture: deadlock, lock-dependency graph. Needs gadget setup to reproduce.

2019 kernel/sched/completion.c: lost waiter, real wake-up protocol error:
    T0: enqueue -> sleeps
    T1: complete -> done 0 to 1 -> wakes T0 -> removes T0 from wait queue
    T2: wait_for_completion -> consumes done 1 to 0
    T0: resumes -> sees done=0 -> goes back to sleep WITHOUT rejoining queue
    no further wakeup possible; a lock was not the missing ingredient.
    WRONG: registering a waiter once remains sufficient across every loop iteration.
    FIX: __prepare_to_swait() inside do_wait_for_common() loop.
    Primary: https://lists.openwall.net/linux-kernel/2019/05/09/1047
    Relevant lecture: condition synchronization, progress, missed wakeups.

2023 PREEMPT_RT kernel/locking/rwbase_rt.c: starvation, not deadlock:
    One writer repeatedly waits for an inode write lock.
    16 readers repeatedly get read lock; none individually waits forever.
    Writer cannot enter; LTP dio_truncate times out after 30 minutes.
    WRONG: since every reader makes progress, the writer must eventually do so.
    FIX: after at least 4 ms blocked, restrict normal-priority reader bias.
    RT or deadline readers can still starve a writer by design (not absolute fairness).
    Primary: https://lkml.iu.edu/2301.2/07043.html
    Relevant lecture: starvation, fairness and progress, RT-specific.

2026 fs/f2fs/checkpoint.c: livelock in file-system checkpoint:
    list head points to an inode currently being freed.
    igrab() cannot take a new reference -> returns failure.
    code retries first item without moving it -> same inode every iteration.
    Meanwhile other dirty inodes are ready, but no progress is made.
    WRONG: retrying a list scan guarantees eventual progress without changing state.
    FIX: list_move_tail before igrab; cond_resched after failed igrab.
    Primary: https://lists.openwall.net/linux-kernel/2026/09/09/2530
    Reviewed commit: https://kernel.googlesource.com/pub/scm/linux/kernel/git/chao/linux/+/e398da0b9131583e0f52bca733eaefc3b3aeae95
    Relevant lecture: livelock distinct from starvation and deadlock.

2026 mm/memory.c device-private migration: HMM livelock / starvation:
    hmm_range_fault repeatedly fails folio_trylock on device-private folio.
    Same CPU is needed by a work item that can release the contested folio.
    Busy retry starves the required work; waiting for lock prevents its release.
    Primary: https://www.mail-archive.com/dri-devel@lists.freedesktop.org/msg588424.html
    Relevant lecture: cross-component progress, kernel + GPU memory management.
    Requires a suitable HMM device-private memory path, not just an arbitrary GPU.

2026 net/sched/act_tunnel_key.c: object retirement breaks RCU reader lifetime:
    updater replaces tc action params; immediately drops old dst reference.
    reader under rcu_read_lock_bh can still have the old params.
    dst_clone sees dying old dst -> reference-count / use-after-free fault.
    Fix defers dst_release until the RCU callback after old readers finish.
    Primary: https://lists.openwall.net/netdev/2026/07/11/140
    Relevant lecture: lifetime, lock-free readers, temporal ordering.
    Needs traffic control tunnel-key action and a reproducible datapath; not in .c demo.

2020 lib/debugobjects.c: a genuine KCSAN race report:
    fill_pool reads obj_pool_free outside pool_lock;
    __free_object changes obj_pool_free concurrently under pool_lock.
    Writer's lock cannot protect a reader who never takes that lock.
    Fix pairs READ_ONCE and WRITE_ONCE on independent diagnostic counters.
    Upstream commit: 35fd7a637c42bb54ba4608f4d40ae6e55fc88781
    Primary: https://lkml.iu.edu/2002.2/06429.html
    Relevant lecture: actual kernel data race, sampled dynamic detector.

2024 kernel/time/timekeeping.c + include/linux/seqlock.h: detector false positive:
    KCSAN reported writes in timekeeping_update racing ktime_get_mono_fast_ns.
    The seqcount latch deliberately permits a reader to touch a stale copy,
    with a validation protocol; unannotated latch confused KCSAN.
    Fix added an instrumentable seqcount_latch API.
    Primary: https://lkml.iu.edu/hypermail/linux/kernel/2411.0/03520.html
    Relevant lecture: false positive from incomplete synchronization semantics.

Kernel equivalents, with the important limitations:
    KCSAN: lib/kcsan/; docs.kernel.org/dev-tools/kcsan.html
      compiler software instrumentation + sampled soft watchpoints.
      detects observed races; does not prove absence; does not detect all atomicity violations.
    lockdep: kernel/locking/lockdep.c; Documentation/locking/lockdep-design.rst
      runtime graph of lock dependencies, potential cycles and IRQ lock misuse.
      NOT Eraser's per-memory-address lockset algorithm.
    LKMM: tools/memory-model/; docs.kernel.org/dev-tools/lkmm/
      herd7 exhaustively checks small concurrent executions against memory-order axioms.
      Models the publish/consume rule; it is not a runtime race detector.
      From a matching kernel source tree, run:
      cd tools/memory-model
      herd7 -conf linux-kernel.cfg litmus-tests/SB+fencembonceonces.litmus
    RCU: kernel/rcu/; include/linux/rcupdate.h
      defers memory reclamation until preexisting readers have left; does not
      automatically defer destruction of objects indirectly held by old pointers.
    seqcount: include/linux/seqlock.h
      readers retry after concurrent writers; KCSAN requires proper annotation.
    DataCollider: originally a Windows-kernel detector using hardware debug registers.
      Linux historical analogue: RaceHound using Kprobes + hardware breakpoints.
      It was an out-of-tree research tool, not mainline Linux.
    Eraser lockset, DJIT+, FastTrack, Atomizer and Velodrome are lecture algorithms,
      not modules that Linux ships under those names. Linux Redflag research
      implemented kernel-specific lockset and atomicity checking outside mainline.

PRIMARY EVIDENCE MAP (original paper -> Linux relationship -> useful real bug)
No algorithm-to-kernel equivalence is asserted unless the implementation
actually uses that technique. Linux lockdep is NOT Eraser.

A. ORDER VIOLATION: pages 9, 11, 18, 54-55.
   Actual Linux: kernel/watch_queue.c watch_queue_set_size vs
   post_one_notification; 2026 v2 publish nr_notes with release; acquire
   before dereferencing notes, after producer initializes other fields.
   WRONG: a nonzero count implies a fully published array even though
   count and pointer were plain independent stores.
   https://lkml.iu.edu/hypermail/linux/kernel/2610.1/04603.html
   The original patch notes GCC 14 on x86-64 could store notes last.
   The code order in C does not by itself prove observer-visible order.
   A historical 2022 pipe notification index-publishing fix is separate:
   https://lkml.rescloud.iu.edu/2203.1/07747.html
   Linux tools: LKMM herd7 and KCSAN (subset). Do NOT claim a clean KCSAN
   run rules out release/acquire ordering bugs.

B. ATOMICITY VIOLATION WITH ATOMIC VARIABLES: pages 10, 68-84.
   Actual Linux: net/tls/tls_sw.c tls_sw_recvmsg vs tls_decrypt_done.
   One CPU sees pending==0 and resets a completion while another CPU is
   between pending decrement and complete(). Atomic decrement does not
   make the dependent reset+signal operation indivisible.
   https://lists.openwall.net/netdev/2020/05/22/305
   Actual Linux: kernel/events/core.c perf_mmap allocation/cleanup vs
   PERF_EVENT_IOC_SET_OUTPUT using an incompletely stabilized rb lifetime.
   https://lists.openwall.net/linux-kernel/2026/02/23/591
   A useful detector needs transaction boundaries; KCSAN alone does not
   infer them. This is precisely why Atomizer and Velodrome exist.
   Original: https://cormacflanagan.com/atom.html

C. DEADLOCK: pages 12, 16.
   Actual Linux: drivers/usb/gadget/udc/core.c locks taken across binding,
   sysfs/regulator/device link chain. Lockdep observed a cycle and
   upstream 1016fc0c096c92dd0e6e0541daac7a7868169903 narrowed scope.
   https://lkml.iu.edu/hypermail/linux/kernel/2209.0/06600.html
   Another: drivers/usb/gadget/composite.c recursive spinlock path
   https://lkml.iu.edu/2101.1/02459.html
   Runtime tool: CONFIG_PROVE_LOCKING, kernel/locking/lockdep.c.
   Lockdep creates lock-order edges; Eraser intersects locksets protecting
   *a memory location*. These are different algorithms.
   https://docs.kernel.org/locking/lockdep-design.html

D. STARVATION AND LIVELOCK: pages 13-14.
   Actual PREEMPT_RT rwbase reader preference: 16 readers can keep writer

G. STATIC TYPE-BASED DETECTION: pages 24-25.
   Source Java studies: M. Naik, Effective Static Race Detection for Java,

H. HAPPENS-BEFORE AND VECTOR CLOCKS: pages 28-33.
   Program order -> release/acquire order -> transitive closure.
   Numeric values FROM LECTURE diagram: A's write stamp=5@A, B sees
   vector (A=5,B=4) after lock. Check 5 <= B.clock[A]=5: YES, that
   write happened before B's access. If a later writer has stamp 6@A
   while B.clock[A] remains 5, 6 <= 5 is FALSE: no causal ordering
   established by this thread clock; if conflicting, race candidate.
   Vector <= is componentwise; join takes maximum componentwise.
   Linux kernel application: Krace combines locksets and HB on ext4,
   btrfs, VFS. Not a mainline kernel module.
   https://ieeexplore.ieee.org/document/9152693/
   Foundational original: Lamport CACM 1978; vector clocks capture
   causality more precisely than scalar timestamps.
   https://dl.acm.org/doi/10.1145/359545.359563

I. DJIT+ EXACT STATE: pages 34-37.
   For each thread: full vector time; for each lock: release clock.
   For each monitored memory cell: R_x and W_x (read and write clocks).
   Write checks earlier reads AND writes against current thread time;
   read checks earlier writes; lock acquire joins saved lock vector;
   release stores thread vector and advances local time.
   Source: Pozniansky and Schuster, PPoPP 2003.
   https://citeseerx.ist.psu.edu/document?doi=7e6135b6603c254308e9d56a8936c9f353c35dbd&repid=rep1&type=pdf
   Kernel analogue: Krace computes precise race evidence from modeled
   primitives, NOT a shipped DJIT+ implementation.

J. ERASER, LOCKSET INTERSECTION: pages 38-42.
   At access, candidate(x) := candidate(x) intersection locks(thread).
   Real issue: one reader need not take the writer's lock, even if
   writer carefully protects all its writes. debugobjects case above.
   BUT: lockless access coordinated by release/acquire or RCU might
   be correct and Eraser can complain because candidate becomes empty.
   Distinguish "unsatisfied locking rule" from observed HB race.
   Original 1997: https://homes.cs.washington.edu/~tom/pubs/eraser.html
   Linux Redflag applied modified lockset with RCU:
   Duggal MSc thesis 2010:
   https://commons.library.stonybrook.edu/stony-brook-theses-and-dissertations-collection/190/
   Seyster PhD thesis 2012:
   https://commons.library.stonybrook.edu/stony-brook-theses-and-dissertations-collection/613/

K. GOLDILOCKS & HYBRID RACE DETECTION: pages 27, 52, 67.
   Key distinction: Goldilocks uses lockset-like structures to track
   an HB relation, not merely Eraser's empty-intersection heuristic.
   Original MSR technical report:
   https://www.microsoft.com/en-us/research/publication/goldilocks-efficiently-computing-the-happens-before-relation-using-locksets/
   Kernel example: Krace combined comprehensive lockset and HB models.
   No claim that Goldilocks is present in mainline Linux.

L. FASTTRACK AND EPOCHS: pages 43-51.
   Last write in a race-free prefix can be represented by one epoch
   5@A, not an entire vector. Test 5 <= current_thread_clock[A].
   For concurrent reads, a read-shared state may require a vector
   again; using one epoch for ALL readers would lose facts.
   Contrast O(thread_count) vector access vs common-case O(1)
   epoch check; not an unconditional per-program speed guarantee.
   Primary original authors: Flanagan and Freund, PLDI 2009.
   https://cormacflanagan.com/atom.html
   ASPLOS 2022 later extends clock-data-structure research:
   https://cs.au.dk/~pavlogiannis/publications/papers/asplos22.pdf
   No FastTrack implementation is shipped as a Linux kernel detector.

M. SAMPLING AND DETECTOR OVERHEAD: pages 52-53, 58-65, 85-88.
   Instrumented load/store -> metadata lookup -> analysis -> writes
   detector state. Multiple CPU updates to shared detector metadata
   require ordering too; detector can materially affect scheduling.
   LiteRace: https://www.microsoft.com/en-us/research/publication/literace-effective-sampling-for-lightweight-data-race-detection/
   Pacer: https://www.cs.utexas.edu/~mckinley/papers/pacer-pldi-2010.pdf
   Research PhD thesis by Daniel Marino on sampling:
   https://www.sigplan.org/Awards/Dissertation/2012_marino.pdf
   KCSAN sampling: https://docs.kernel.org/dev-tools/kcsan.html
   Real blind spot: slub.o excluded => exact zero chance of reports
   whose both accesses reside in uninstrumented compilation unit.

N. COLLISION AND DATACOLLIDER: pages 58-66.
   Halt a sampled access, watch its physical address interval, detect
   a conflicting overlapping access; no need to infer HB to see pair.
   DataCollider originated on Windows; x86 DR0-DR3 hardware breakpoint
   slots are scarce. Its Linux historical analogue is RaceHound, which
   places Kprobes at selected instructions and hardware data breakpoints.
   RaceHound original announcement May 2015:
   https://lkml.iu.edu/hypermail/linux/kernel/1505.2/04290.html
   RaceHound paper 2013:
   https://www.ispras.ru/en/publications/2013/on_the_implementation_of_data_breakpoints_based_race_detection_for_linux_kernel_modules/
   Original DataCollider OSDI 2010:
   https://www.usenix.org/conference/osdi10/effective-data-race-detection-kernel
   Modern KCSAN has SOFTWARE sampled watchpoints, not x86 DR registers.
   Collision miss can mean sampled timing did not overlap, not safe code.
   RaceChaser 2017 from the IITK instructor's research:
   https://www.cse.iitk.ac.in/users/swarnendu/files/papers/racechaser-caper-cc-2017.pdf
   No Linux RaceHound reproduction should be claimed from old source
   alone on 7.x kernels; compatibility and access need checking.

O. MODEL CHECKING: page 66.
   Define a small state space and search possible operations; this
   requires a correct model. For memory ordering use:
   tools/memory-model, herd7, linux-kernel.cfg. Official:
   https://docs.kernel.org/dev-tools/lkmm/docs/litmus-tests.html
   For thread schedule+input exploration:
   Snowboard SOSP 2021, 14 bugs, 12 confirmed; not mainline.
   https://research.google/pubs/snowboard-finding-kernel-concurrency-bugs-through-systematic-inter-thread-communication-analysis/
   Do NOT mistake "herd7 reports a permitted outcome" for an observed
   kernel crash. To test the watch-queue publication fix, construct an
   LKMM litmus that models the exact writes to pool fields and count,
   paired with observer's count test and pointer read, and compare
   allowed results before/after store_release/load_acquire. Any
   approximation that changes the branch or link may change outcomes.

P. PREDICTIVE CP, WCP, DC: page 67.
   Predictive analysis seeks conflicting re-orderings not seen as
   adjacent in the recorded test. HB detects races in observed trace;
   a weaker-than-HB predictive order can expose alternative valid
   schedules. WCP extends CP and detects more predictable races.
   https://pldi17.sigplan.org/details/pldi-2017-papers/14/Dynamic-Race-Prediction-in-Linear-Time
   CP original: Smaragdakis et al POPL 2012 as cited by lecture.
   A code-only runtime execution cannot establish predictive
   soundness; need event trace, precise sync semantics, and a
   schedule witness that actually executes on a chosen kernel.
   Krace fuzzing + Snowboard pairwise communication are related
   kernel research but NOT implementations of CP/WCP/DC.

Q. RACE-FREE DOES NOT GUARANTEE ATOMICITY: pages 68-70.
   StringBuffer length() and getChars() each synchronized separately;
   a competing resize can run between calls. Individual operations
   are safe; "length and subsequent copy refer to one snapshot" fails.
   Linux direct analogue: perf rb lifetime between setup and
   cleanup; TLS pending/reset/notify dependence.
   A lock across every read/write of a field is not proof that a
   group of calls behaves as one transaction.

R. LIPTON REDUCTION, ATOMIZER: pages 71-77.
   Operations that commute past actions from other threads are movers:
   right mover moves right; left mover moves left; both does both;
   non-mover cannot be legally swapped. Sufficient serial form:
   right* [at most one nonmover] left*.
   Example grounded in Linux TLS fix: an unprotected
   reinit_completion cannot in general commute with complete()
   from another thread, because their swap changes what next wait
   observes. THIS is a causal interpretation, not an Atomizer runtime
   report from Linux.
   Original: C. Flanagan and S. Freund, POPL 2004.
   https://cormacflanagan.com/atom.html
   Kernel-level actual logging and atomicity checkers:
   Justin Seyster PhD dissertation 2012 above.

S. VELODROME / SERIALIZABILITY: pages 78-84.
   Unit = transaction (atomic region). For conflicting accesses
   between transactions add dependency edges in observed execution;
   a directed cycle rules out an equivalent serial transaction order
   for that trace. Avoid edges for independent memory locations.
   Acyclic graph is NOT proof every possible run is safe.
   Unary transactions (events outside marked atomic blocks) can
   overwhelm memory. Garbage collection/pruning of completed nodes
   with no incoming edges is part of the studied method.
   Original: Flanagan, Freund, Yi, PLDI 2008.
   https://cormacflanagan.com/atom.html
   AeroDrome ASPLOS 2020 achieves linear time using vector clocks:
   https://www.comp.nus.edu.sg/~umathur/papers/aerodrome-asplos2020.pdf
   Real kernel targets: TLS completion and perf rb lifetime; without
   explicit transaction semantics no claim that Velodrome finds them.

T. TEST OBSERVATION VS EXPLOIT/PROOF: pages 17, 22, 23, 52, 66, 88.
   A *historical fix* proves maintainers accepted a change, not that
   the bug is still present in a current stable or distro kernel.
   KCSAN report = observed conflict or changed-value watchpoint;
   not automatic use-after-free proof. Lockdep cycle may be real
   or may be a lock-class abstraction artifact (Nov 2026 power_supply).
   Clean test on one machine cannot prove absence of all interleavings.
   Controlled negative tests are necessary: churn without shrink in
   the 2026 SLUB report produced zero reader-pair reports while
   churn+shrink with compiler instrumentation produced hundreds.

HOW TO BUILD A REAL KERNEL INVESTIGATION (not toy simulations)
1. Choose a concrete upstream report and commit. Record full patch ID,
   kernel configuration, state before the change and exact observed trace.
2. Locate entry syscall, user-visible consequence, data fields and
   both CPU call chains. Record lock, lifetime and visibility assertions.
3. Construct a *pre-fix* kernel build in an isolated disposable VM.
   Confirm the vulnerable code still exists by inspecting its tree.
4. Use the smallest real user workload from reporter: watch/keyctl
   (unprivileged), perf mmap+redirection, USB gadget (needs virtual UDC),
   f2fs image/mount, or kernel test module SLUB shrink+churn.
5. Run CONFIG_KCSAN and CONFIG_PROVE_LOCKING separately, record
   false negative due to explicit file exclusions/false lock-class
   reports, then use LKMM to model ordering. Do NOT assume one detector
   answers all questions.
6. Apply exact upstream fix with matching context, run the SAME workload,
   check that failure no longer occurs and that no unrelated regression
   appears. Reproduction may still be probabilistic even pre-fix.
7. Preserve kernel .config, uname, source commit, dmesg, sched traces,
   crash stack, exact build commands, before/after verdict, and negative
   control. No fictitious "100% reproduced" claims.
